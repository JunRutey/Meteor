# ADR-023 · 人物档案拆成「备注」和「正文」，编辑页改为可滚动布局

- 状态：已接受（v0.4）
- 影响：`:core-storage`、`:feature-people`、`:app`
- 相关：[ADR-020](ADR-020-person-profile-editable-and-image-deletion.md)

## 一、为什么要有两个字段

ADR-020 给人物档案加上了编辑入口，但**只有一个**文本框（当时叫「备注」）。
实际用下来：用户想写「这个人是谁」的长文（可插图），也想记一句「大学同学」的短提示，
两者塞进同一个框，写什么都变成「备注」，正文无处可写。

**决策**：`PersonProfile` 拆成两个字段。

```markdown
name: 小明
relation: friend
note: 大学同学          ← 备注，一行
---
正文（Markdown，可插图、可加链接）   ← 正文
```

- `note` 放在**头部**，天然只能是一行；写入前把换行压成空格，避免破坏行式头部。
- `notes` 仍然是 `---` 之后的自由正文，格式完全不变。
- 详情页分两段显示：「备注」一行 + 「正文」Markdown 渲染，各自带独立编辑入口。

## 兼容性（关键）

这是**纯增量**的格式变更：

| 情况 | 结果 |
|---|---|
| 旧文件（没有 `note:`） | 读回来 `note` 为空，原内容仍是正文 ✓ |
| 旧版本读新文件 | 忽略 `note:` 行，正文照常读到（只是短备注看不见）✓ |
| 新版本读新文件 | 两个字段都对 ✓ |

所以不需要迁移脚本。已经写下的内容会出现在「正文」里——它本来就是正文。

## 二、编辑页为什么必须改成可滚动

键盘弹出后，人物编辑页的输入框被压成一条线：页面用的是
`fillMaxSize` + `weight(1f)` 的固定结构，头部、称呼、关系、标签全在抢同一块高度，
唯一可伸缩的那一格（编辑器）最后只剩几十像素，而且整页不能滚，够不到其它字段。

**决策**：

- 头部固定（标题 + **保存 / 返回**，保存从底部挪到头部，底部大按钮同样在抢高度）；
- 中间表单 `weight(1f) + verticalScroll`，键盘挤掉多少就能滚多少；
- 正文编辑器给**固定高度**（320dp）并用 `fillMaxSize` 填满那个盒子——
  在可滚动父容器里再放 `weight` 会因为约束无界而塌成 0，这正是第一个 bug 的成因。

## 后果

- 人物页现在有 6 个可编辑点（称呼、关系、备注、正文内联图片/链接、预览），
  但任何高度下都能滚到。
- 正文编辑器高度固定，长文在框内滚动；这是「表单里嵌编辑器」的标准取舍。
- 头部放保存按钮，单手够到的成本比底部略高，换来的是键盘弹出后不用再找按钮。

## 补充（v0.4，第二部分被 ADR-024 取代）

上面「二、编辑页为什么必须改成可滚动」的结论只解决了一半问题。装到真机上才发现：
键盘弹起时**整个窗口被系统平移**，固定表头和「保存」一起被顶出屏幕，
页面还会"咚"地跳一下（见 [ADR-024](ADR-024-window-insets-and-ime.md)）。

**现行做法**：

- 页面**不再整页滚动**。头部固定，称呼／关系／备注在上，正文编辑器 `weight(1f)`
  吃掉剩下的高度——键盘弹起只压缩编辑器，页面本身不动。
- 中间的身份区仍可滚动，但被限制在可用高度的 42% 以内：屏幕很矮时编辑器不会被挤成 0。
- 编辑器高度不再固定 320dp（那是"整页滚动"方案的补丁）。

即：**ADR-023 的第一部分（备注 / 正文 两个字段）仍然有效，第二部分（可滚动整页 + 固定高度编辑器）已被取代。**
