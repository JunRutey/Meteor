# ADR-020 · 人物档案可编辑；图片可删除

- 状态：已接受（v0.4）
- 影响：`:core-storage`、`:feature-editor`、`:feature-people`、`:app`

## 一、人物档案只能建、不能改

v0.5 的「人际关系」实现了建档与详情页，但**没有任何入口修改已有档案**：
建档对话框只收「称呼 + 关系」，备注字段从来没有被写过，详情页永远显示「（暂无备注）」。
`PersonQueries.update(...)` 其实早就写好了，只是没人调用。

**决策**：新增 `people/{person_id}/edit` 路由与 `PersonEditScreen`，可改称呼、关系、
备注，并把它接进详情页的「编辑」按钮。

备注是 Markdown 正文，所以直接复用 `:feature-editor` 的 `MarkdownField`：
加粗、插图、插链接、预览全套能力都有，光标映射也只需要维护一份。

因此新增一条依赖边：**`feature-people → feature-editor`**（已在档案 §3 与
`tools/check-module-graph.sh` 的白名单里登记）。方向仍单向无环：
`app → feature-people → feature-editor → core-storage`。

图片落盘位置沿用既有规则：`EncryptedImageStore.save(bytes, personId)` 会写进
`数字遗产/图片/<person_id>/`，与档案 §4 的目录树一致，不会混进 `_self`。

## 二、图片插错了就删不掉

插入图片只是往正文追加一段 `![](meteor://image/<token>)`，没有任何删除入口：
引用留在正文里、密文留在磁盘上，图片库也一直能看到它。

**决策**：分两层，缺一不可。

1. **正文层**：`MarkdownEditing.removeImage(body, token)` 是纯函数，删掉那一条引用；
   若该行只剩下引用，整行一起去掉（否则每删一次就多一个空行）。可单测。
2. **文件层**：`ImageStore.delete(token)` 删除密文。`ImageStore` 不是冻结接口，
   新增方法不破坏 R2。

UI 上：编辑区工具栏下方出现**图片条**——正文里引用到的图片缩略图，每张右上角一个
`×`，点击弹确认框。

## 三、删除的时机：保存成功之后

文件不能随点随删。用户可能删了图片又放弃本次编辑，此时磁盘上的记录仍然引用它，
提前删文件等于凭空把旧日记的图打碎成「图片无法显示」。

**决策**：先从正文移除引用（立即，可见），把 token 记进 `pendingDeletes`；
**保存成功后**才真正删除文件。保存失败则文件原样保留，下次仍可重试。

## 限制（已知）

- 没有引用计数：同一 token 若被复制到多条记录里，从任意一处删除都会让另一处失效。
  当前没有任何 UI 能制造共享引用（插图总是产生新 token），风险仅存在于手工复制正文。
- 删掉引用但放弃保存，会在磁盘上留下一个没有引用的图片，仍出现在图片库里。
  宁可留垃圾，不可碎图。
- 人物档案的「相关记录」仍然为空：目前没有任何入口创建**归属于某个人物**的记录
  （`person_id != null` 的日记/聊天）。这是 v0.6 的事，不在本 ADR 范围内。
