# ADR-043 · 打赏页重排与支付宝入口

- 状态：已接受
- 影响：`:app`（打赏页与外部链接处理）、`:app` 资源（文案）

## 一、问题

旧打赏页只有一个铺满卡片宽度的微信赞赏码：

- 二维码被放大器撑到整页宽，首屏几乎只有一张图，页面没有说明；
- 没有支付宝入口，用户只能使用微信；
- 没有说明打赏与功能权限的关系，容易被理解为付费解锁。

需求是：重排打赏页，保留微信赞赏码，并增加一键跳转支付宝打赏。

## 二、决定

打赏页沿用关于页的「返回箭头 + 标题 + 圆角卡片」外壳，卡片内分两块：

### 2.1 支付宝

- 区块标题「支付宝」，一句说明文字；
- 主按钮「支付宝打赏」，整行宽度、48dp 高、24dp 圆角，与设置页按钮一致；
- 点击后用 `Intent.ACTION_VIEW` 打开
  `https://qr.alipay.com/fkx10823u6zc2mnhhn6h4de`；
- 启动失败（没有浏览器、没有能处理该链接的应用等）时用 Toast 提示，不静默失败。

### 2.2 微信

- 区块标题「微信」，一句说明文字；
- 赞赏码居中显示，最大宽度 240dp（要求范围 220–260dp），按图片自身宽高比
  等比缩放，16dp 圆角；
- `assets/donate.png` 缺失或解码失败时显示说明文字，不显示空白页。

### 2.3 边界说明

卡片底部增加一句「打赏是自愿支持，不会解锁任何功能或数据」。
打赏与功能权限、AI 用量、数据可见性之间没有任何代码关联；本次只是新增展示和
外链入口，没有新增支付回调、订单、账号或校验逻辑。

## 三、为什么用外链而不是支付宝 SDK

- 需求只要求一键跳转，官方收款二维码链接已经能完成支付；
- 引入支付宝 SDK 会增加依赖、打包体积、混淆规则与隐私说明，收益仅为少一次跳转；
- 不引入 SDK 就不需要新增权限、签名配置或密钥，符合本项目“本地优先、依赖尽量窄”的取向；
- URL 是数据常量，放在 `AboutLinks.kt`，与仓库 / 讨论 / 邮箱常量集中管理；
  所有可见文案仍在 `strings.xml`。

## 四、被否掉的方案

- **把支付宝二维码也做成图片资源**：需要维护第二张图片，且无法保证与官方收款页
  一致；外链由官方页面负责金额与支付流程。
- **用支付宝 SDK / 原生支付页**：为一个打赏按钮引入完整 SDK，不划算。
- **保持旧版大图**：没有说明与分区，微信二维码在平板上被放大到失真。
- **微信与支付宝并排两列**：二维码与按钮宽度不一致，窄屏会挤压说明文字；
  上下两块更符合设置页的纵向节奏。
- **在打赏页增加“已打赏”状态或权益**：打赏明确不解锁任何功能，不应制造虚假承诺。

## 五、风险与已知限制

- 链接能否打开取决于设备是否安装浏览器或支付宝；失败时只提示，不内嵌 WebView。
- 支付宝收款链接由维护者维护；若链接失效，需要在 `AboutLinks.kt` 更新常量并重新发版，
  应用内没有远程配置。
- 微信赞赏码继续依赖 `assets/donate.png`；缺图时页面仍有完整说明，不会空白。
- 打赏完全自愿，应用无法验证是否支付成功，也不提供退款、发票或权益查询界面。
- 不改变任何数据格式、模块依赖或冻结接口；`tools/check-module-graph.sh` 的边表不变。
