# ADR-034 · 人物档案可删除、自定义标签与详情页重做

- 状态：已接受
- 日期：2026-11-14
- 关联：ADR-014（person_id 目录）、ADR-020（人物档案可编辑）、
  ADR-023（备注与正文分离）、ADR-028 / ADR-030 / ADR-032（AI 写权限与删除边界）

## 背景

人际关系功能目前能建档、能编辑，但**没有任何删除入口**：用户建错人或不再想保留某个人的档案时，
只能让它永久占着列表。新建对话框里的三个关系标签是写死的枚举，无法记录「同事」「大学同学」这类
更贴近用户的称呼。建完档点进详情页后，界面仍是 v0.5 的旧结构：页头和备注占住固定高度，只有
「相关记录」在滚动，正文稍长就会被截断，也与后来重做的日历 / AI / 搜索页面风格不一致。

## 决定

### 1. 删除只删人物档案本身

`PersonQueries` 新增窄接口：

```kotlin
fun delete(personId: String): PersonDeleteResult
```

- 只接受 `person_id`，由既有的 `PERSON_ID_PATTERN` 校验，不接受路径或文件名；
- 删除 `记忆档案/人际关系/<person_id>/` 整个目录（`profile.md` 及未来落在该目录内的文件）；
- 日记、导入的附件、图片与数字人格属于不同存储，**不在这里级联删除**；
- 目录已不存在时返回 `NOT_FOUND`，让重试保持幂等；
- 详情页删除后弹出返回栈，同时通过 `SearchService.removeRecord` 移除索引里的 profile 行，
  避免搜索里留下已删除的人。

UI 侧在详情页右上角「更多」菜单里提供删除，删除前必须二次确认；确认文案明确说明
「相关日记和已导入的文件不会被删除」。

### 2. 自定义标签是纯增量的文件格式变更

`PersonProfile` 新增 `tags: List<String>`，写入 header：

```markdown
name: 小明
relation: friend
note: 大学同学
tags: 同事, 大学同学
---
正文
```

- 三个内置关系仍是结构化的 `Relation` 枚举：`relation` 行和 AI 工具里的 `family` /
  `friend` / `former_friend` 都不变；
- `tags:` 只是补充的自由文本，按逗号分隔，写入前统一去空白、去重、每个最多 24 字、最多 8 个；
- 旧文件没有 `tags:` 行，读回来就是空列表；旧版本读新文件会忽略这一行，profile 其余字段照常可读；
- 因此不需要迁移脚本，备份导出的 Markdown 仍然可读。

UI 上把「内置关系 + 自定义标签」合并成一个标签编辑器，建档对话框和编辑页共用：
点内置关系决定 `relation`，输入框添加的文本进入 `tags`，点 `×` 移除。

### 3. AI 工具同步扩展

- 新增 `delete_person(person_id)`：登记为 `WRITE_PEOPLE`，**每次调用都要求应用内确认**，
  并且在「人物对话」作用域（`allowedPersonId != null`）里直接拒绝，避免模型删除正在对话的人；
- `create_person` / `update_person` 新增 `tags` 数组参数；`read_person` / `list_people`
  返回 `tags`；
- `update_person` 不提供 `tags` 时保留原标签，显式传空数组才清空；
- 删除仍然只能按 `person_id`，AI 拿不到任意路径、附件或记录 ID 的删除能力。

### 4. 三级详情页重做

新的 `PersonDetailScreen` 与当前 UI 语言一致：

- 手绘图标（返回 / 编辑 / 更多 / 关闭），不再依赖 Material 图标包；
- 页头 64dp，下面是 24dp 圆角的人物卡：首字母头像、称呼、关系与标签胶囊、一行备注；
- 备注、正文、相关记录都是圆角卡片，**整页由一个 LazyColumn 滚动**，长正文不再被截断；
- 相关记录的导入 / 导出、错误与导入摘要沿用原有状态，只改变呈现方式；
- 删除入口在「更多」菜单里，红色文字，二次确认。

## R1 模块准入五问

1. **模块归属：** 数据与删除在既有 `:core-storage`；标签编辑与详情页在既有 `:feature-people`；
   AI 工具在既有 `:feature-ai`。不新增模块。
2. **依赖方向：** 没有新增依赖边。`app → feature-people → core-storage`、
   `feature-people → feature-editor`、`feature-ai → core-storage` 全部保持不变且无环。
3. **对外接口：** `PersonQueries.delete(personId)` / `tags` 参数只暴露业务字段；
   `person_id` 必须匹配既有路径白名单正则；AI 的 `delete_person` 只接受同一个字段。
4. **可移除性：** 移除 AI 后档案与删除仍可用；移除人际界面后文件仍是普通 Markdown，
   备份和存储层可独立读取。没有跨模块硬依赖。
5. **数据格式：** 仅新增可选的 `tags:` header 行，向后兼容；不改变目录结构、加密方式或现有字段。

## 已知限制

- 删除人物不会清理该人物名下的附件、图片和数字人格快照；这些数据仍在各自的管理入口可见
  （「记录」页、图片库）。这是有意的窄删除：宁可留下可单独清理的产物，也不让一次确认
  静默删掉可能被其它记录引用的图片。
- 写过 `meteor://person/<person_id>` 链接的日记不会自动改写；链接会指向已删除的人物，
  正文内容仍然保留。
- 删除后索引行的清理在应用内完成；如果用户绕过应用直接删文件，索引会在下次启动重建时收敛。
