# ADR-042 · 关于页收口、问题反馈与两级更新日志

- 状态：已接受
- 影响：`:app`（关于 / 反馈 / 更新日志界面与导航）、`:feature-settings`（设置页入口）

## 一、问题

旧的「关于」页把 `assets/about.md` 的整篇介绍直接铺在页面上，然后才是 GitHub
仓库按钮；用户想找更新日志、讨论区或反馈渠道，需要先读完一篇说明。同时：

- 更新日志是单页：26 个版本、近 900 行 Markdown 一次性渲染，既难滚动定位，
  也让页面首屏非常长；
- 设置根页的「关于」区同时有关于、打赏、更新日志三个入口，与关于页里的
  仓库入口并列，入口重复且层级混乱；
- 仓库的议题（Issues）与讨论（Discussions）没有入口，用户只能先去仓库再找；
- 没有应用内可复制的反馈邮箱。

## 二、决定

### 2.1 关于页只保留身份与四个入口

关于页不再读取或渲染 `about.md`，改为：

1. 应用名 + 版本号；
2. 一个圆角卡片内的可点击行：更新日志、项目仓库、讨论、问题反馈。

入口数据：

- 仓库：`https://github.com/JunRutey/Meteor`
- 讨论：`https://github.com/JunRutey/Meteor/discussions`
- 议题：`https://github.com/JunRutey/Meteor/issues`
- 邮箱：`JunRutey@outlook.com`

URL 与邮箱是**数据常量**，集中在 `AboutLinks.kt`，不当作中文文案；所有可见标签
都在 `app/src/main/res/values/strings.xml`。

### 2.2 议题收进「问题反馈」二级页

关于页的「问题反馈」进入独立二级页，页内只有两行：

- GitHub 议题（打开仓库 Issues）；
- 邮箱反馈（`mailto:`，副标题直接显示邮箱地址）。

这样关于页保持四个入口，议题仍然可达，但不会把「提 issue」放在关于一级页。
外部链接与邮件都通过 `Intent.ACTION_VIEW` 打开；没有可处理的应用时给出提示，
不静默失败。

### 2.3 更新日志改成两级页面

- **版本列表（二级）**：解析 `assets/changelog.md`，每个 `## vX.Y.Z` 一行，
  按文件顺序显示（最新版本在最上），行样式与设置页一致，点击进入详情。
- **版本详情（三级）**：标题为「更新日志 · vX.Y.Z」，正文用轻量 Markdown 行渲染：
  `###` 小节标题用主题色加重，`-`/`*` 列表转成圆点，普通行按正文样式，空行留
  间距。列表与详情都复用「返回箭头 + 标题 + 圆角卡片」的 `AboutPage` 外壳。

导航新增 `about/feedback` 与 `about/changelog/{version}` 两个 route；版本号是路径
参数，跳转前做 URI 编码，返回栈由 Navigation Compose 正常维护。

设置根页的「更新日志」行移除，只保留「Meteor 版本号（进入关于）」与「打赏」；
更新日志入口统一放在关于页，避免两个入口并列。

### 2.4 解析器

`ChangelogParser` 是 `:app` 内的纯 Kotlin 对象，不依赖 Android、不引入 Markdown
库。它把文本切成 `ChangelogVersion(number, lines)`：

- 空文件、没有 `## ` 版本行的文本返回空列表；
- 版本按出现顺序保留，不排序、不改写版本号；
- 第一个版本之前的内容忽略；
- `###` 小节与普通行原样留在该版本的 `lines` 中，由界面决定渲染方式；
- 每个版本去掉首尾空行，保留版本内部用于分段的空行。

解析逻辑由 `app/src/test` 的 `ChangelogParserTest` 覆盖：空文件、无版本、多个
版本顺序、带 `###` 小节、空版本正文、非法版本标题。界面本身不写单元测试。

## 三、为什么不改模块

- 关于、反馈、更新日志都依赖 Compose 与导航，属于 `:app` 的组装层；
- 解析器是纯数据逻辑，放在 `:app` 的 `ui/about` 下即可被同模块单测覆盖；
- 不新增模块、不新增模块依赖边，`tools/check-module-graph.sh` 的依赖表不变；
- 没有数据格式变更：`changelog.md` 仍是发布流程维护的 Markdown 数据文件，
  本次只是换了读取与展示方式。

`about.md` 仍保留在 assets 中，但不再被界面加载；它是否作为文档资产继续维护，
留给后续整理，不影响本次功能。

## 四、被否掉的方案

- **在关于页里继续渲染 `about.md`，把入口放在文末**：正文仍然占据首屏，用户
  还是要先读完介绍才能找到链接，与需求相反。
- **把议题直接放在关于页一级**：需求明确要求议题归属于问题反馈；放在一级会让
  关于页变成五个入口，层级更乱。
- **更新日志继续单页，只加锚点**：没有版本列表可点，长页面定位问题没有解决。
- **在 WebView 里渲染 changelog**：引入 WebView 与额外加载状态，视觉也无法与
  应用卡片风格统一。
- **引入第三方 Markdown 渲染库**：只为 `###` 与列表付出依赖与体积成本不划算；
  现有 `DocsLine` 风格已足够。
- **把 changelog 拆成多个资源文件**：发布流程仍需维护一个可整体阅读的文件，
  解析成本很低，拆分反而增加维护负担。

## 五、风险与已知限制

- 更新日志依赖 `changelog.md` 的 `## ` 版本标题约定；若将来改格式，需要同步
  更新解析器与测试。解析器对不合规内容的选择是“忽略或并入当前版本”，不会崩溃。
- 外部链接与 `mailto:` 是否可打开取决于设备上是否安装浏览器 / 邮件应用；应用
  会提示失败，但不提供内置浏览器或邮件撰写页。
- 更新日志列表按文件顺序展示，不在代码里比较版本号大小；发布时仍需保证
  `changelog.md` 最新版本在前，这与既有发布约定一致。
- 关于页不再展示 `about.md` 的介绍，用户了解原理需要查看仓库文档；这是本次
  需求的有意取舍。
